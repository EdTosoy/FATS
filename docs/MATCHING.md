# Explainable resume comparison — Phase 6

**Private beta pause:** Phase 6 is preserved but inaccessible by default. `FATS_AI_MATCHING_ENABLED` must be exactly `1` on the server to expose its application panel and API; unset/other values deny all matching requests before service/provider/extraction access. Keep it unset or `0`. Provider credentials alone cannot enable it. No AI work or evaluation is authorized during private beta readiness. The configuration and journeys below describe the historical capability, not current beta availability. See [local configuration](LOCAL_CONFIGURATION.md) and [readiness](PRIVATE_BETA_READINESS.md).

This is an optional, account-only comparison of one immutable resume version with one saved job description. It never edits resume bytes, records a submitted resume, changes an application, follows source links, or runs when a file is uploaded. Guest tracking, interviews, document management, and Sidekick keep their existing behavior. No general chatbot, rewriting, hiring prediction, percentage score, or automatic application is included.

## User journey and consent

Open a saved application, choose an exact resume version, and select **Review text before comparing**. FATS authenticates the verified account, checks both parents, verifies file integrity, extracts text locally, and stages a private 15-minute preview. This step makes no provider request. Review both displayed sources and extraction warnings, then explicitly acknowledge external sharing and select **Send reviewed text and compare**. Cancelling makes no provider request; staged text expires and is removed on later comparison access. Selecting another version or retrying a failed analysis requires another review and confirmation. No provider configured means an honest unavailable state; it never substitutes a mock result.

Only normalized, best-effort contact-redacted resume/job text, segment IDs, and requirement-priority hints are sent. Original files, filenames, account IDs, application IDs, storage keys, source URLs, and account profile fields are not sent as metadata. The account name, obvious first-line names, email addresses, phone-like numbers, URLs, and explicitly labelled personal-information lines are removed where recognized. Personal details elsewhere can remain: this is **not guaranteed anonymization**. Users must review the text and cancel if it contains information they do not want to transmit. FATS does not currently provide an extracted-text editor; upload a cleaner resume or correct the saved job description and review again.

## Extraction boundary

No new parsing dependencies were added. The adapter reuses installed PDF.js **6.4.299** for PDF text and saxes **6.0.0** after the Phase 5 ZIP/CRC/Open XML validation for DOCX. Upload validation remains separate: uploading never extracts or analyzes. Missing/corrupt private bytes block extraction and retain original metadata/history.

| Boundary             | Limit / behavior                                                                                                                                            |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Original file        | Existing nonempty PDF/DOCX, at most 10 MiB, existing supported format subset                                                                                |
| PDF                  | At most 30 pages; native worker, 10-second deadline, 128 MiB old/16 MiB young V8 heap and 4 MiB stack                                                       |
| Extracted resume     | At most 24,000 characters and 200 segments; reject excessive content rather than silently truncate                                                          |
| Job description      | Saved plain text only; existing 20,000-character application limit, at most 200 normalized segments                                                         |
| Combined input       | At most 48,000 UTF-8 bytes including segment metadata, before provider framing/instructions/schema                                                          |
| DOCX                 | Existing ZIP expansion/entry limits; UTF-8 body XML, maximum depth 100; no macros, DTD, embedded objects, disk extraction, or external-reference resolution |
| Extraction admission | One per account, two globally; 20 attempts/account and 100/global per UTC day, including failures                                                           |

Results distinguish `success`, `empty`, `unsupported`, `failed`, and `limit`. Blank documents are empty; image-only documents and PDFs with an image-only page are unsupported. Malformed documents fail safely. There is no OCR. PDF reading order can differ from visual layout, and images on text-containing pages can contain omitted information. DOCX extracts body paragraphs; headers, footers, drawings, and some text boxes may be omitted. Warnings and a full source review precede sharing; no missing information is filled in. Citations refer to extracted, whitespace-normalized, redacted text, not original byte offsets or exact visual coordinates.

PDF extraction calls text/operator APIs without rendering interactive layers, executing document actions, fetching links, loading XFA, or enabling document scripting. Parser diagnostics are suppressed. V8 worker limits do not bound every native/external allocation and are not an OS security boundary. DOCX runs bounded validation/parsing in the server process. These controls are not malware certification; a hosted service needs a separately reviewed isolated extraction service and stronger global resource admission.

## Provider architecture and configuration

`MatchingProvider` is a server-side interface with configuration identity, user-visible label, external-transmission flag, and an abortable analysis method. The initial adapter calls the fixed OpenAI Responses endpoint over HTTPS using a server-only `OPENAI_API_KEY`, JSON Schema Structured Outputs, `store:false`, and no tools, browsing, file upload, conversation history, or automatic retries. It pins **`gpt-5.4-mini-2026-03-17`**, with `reasoning.effort: none`, a 4,000-output-token ceiling, and a 128,000-byte response ceiling. The snapshot supports Structured Outputs; pinning avoids silent alias changes. Model, prompt, schema, extraction and validation changes must deliberately version the provider configuration and get evaluated before release. The current provider contract uses `MATCHING_CONTRACT_VERSION` (`matching-v1-contract-v2`), composed with the base extraction/domain version `MATCHING_VERSION`; historical report identities remain unchanged. Provider failures/refusals/incomplete/invalid responses return fixed safe states, never raw payloads. The contract schema uses nested classification-specific `anyOf` branches: demonstrated/partial require 1–3 citations, undocumented requires an empty evidence array, and unclear permits 0–3 context citations. Instructions distinguish supporting evidence from negative statements and preserve academic versus professional scope. Server validation stays authoritative; results are never relabeled or stripped of evidence to force acceptance.

Add optional settings to the private ignored `apps/web/.env.local` and restart the server:

```dotenv
FATS_AI_PROVIDER=openai
OPENAI_API_KEY=replace-with-a-private-project-key
FATS_AI_DAILY_ACCOUNT_LIMIT=5
FATS_AI_DAILY_GLOBAL_LIMIT=20
FATS_AI_TIMEOUT_MS=30000
```

The server opt-in `FATS_AI_MATCHING_ENABLED=1` is additionally required, only after separate authorization to resume AI. Leave it unset/`0` for beta. Never use `NEXT_PUBLIC_` for credentials. Invalid limits fail closed. Account limits allow 1–50, global limits 1–500, and timeout 1–60,000 ms; these are operator settings, not client input. With the feature explicitly enabled, leaving `FATS_AI_PROVIDER` unset disables new provider work while allowing report reads/deletion. The beta gate instead denies all matching actions, preserving historical records and their parent protections. Keys, resumes, extracted text, model requests/responses, and raw errors must not enter logs or telemetry.

OpenAI's API data controls state that API data is not used for training by default, while abuse-monitoring logs can generally retain content for up to 30 days, with exceptions. `store:false` disables Responses application-state storage; **it does not itself establish zero retention**. Provider terms, organizational controls, subprocessors, region availability, and applicable privacy requirements must be reviewed before external users or sensitive data. FATS configures neither Zero Data Retention nor regional processing. Local report deletion does not revoke provider-side retention or remove earlier operator archives.

Official standard pricing checked on 2026-10-16 is USD **$0.75/million input tokens and $4.50/million output tokens** for the selected model. For illustration, 10,000 input and 2,000 output tokens cost approximately $0.0165; actual input includes instructions/schema and varies with text/tokenization. The 48,000-byte bound is not a token count. Rates can change. Persistent UTC-day counters reserve an attempt transactionally **before** an external call; default caps are 5/account and 20 for the entire server. Failed, timed-out, refused, and invalid-output calls consume attempts because a provider may charge them. One analysis can run per account, and at most 20 reports are retained per account. Report deletion does not reset usage. Idempotent retries of the same preview return its existing report without another call; conflicting request-ID reuse is rejected. There is no automatic retry or billing system. Use provider project budgets/alerts as a separate operational control; local caps are attempt limits, not a guaranteed currency budget.

## Results and trust boundaries

`libs/domain/src/matching.ts` defines source segments, citations, priorities, classifications, and strict result validation without UI/server dependencies. Provider results can contain only up to 12 quoted requirements, a classification, and up to three quoted resume references each. Unknown fields, arbitrary prose, invented skills/examples, scores, duplicate requirements, invalid IDs, absent excerpts, and placeholder citations are rejected. FATS supplies cautious, actionable suggestion templates rather than allowing unconstrained generated advice.

Each citation must be a contiguous exact substring in its claimed source segment. FATS calculates UTF-16 start/end offsets and stores the source snapshot with the report; the UI exposes IDs, page/paragraph/line locations, offsets, and complete reviewed sources. The original bytes remain immutable. Required/preferred/unclear priority derives from explicit wording or supported section headings. Ambiguous requirements remain unclear instead of inventing employer policy.

“Evidence found” (`demonstrated`) and “Partially documented” require resume citations and meaningful lexical overlap. Demonstrated additionally requires coverage of all meaningful quoted requirement terms, exact numeric tokens, and no recognized negation/learning/aspiration wording. “Not documented” cannot carry supporting resume evidence and **never means the person lacks that skill**. “Needs clarification” invites user/employer confirmation. These conservative checks reject some legitimate synonyms or paraphrases. Exact citations and token coverage do not prove semantic entailment, resume truth, requirement completeness, or real-world competence. The model can still misunderstand context or omit requirements. The report explicitly calls assessments suggestions to review, not verified qualifications. No live-model quality benchmark has been run in this phase.

Documents, saved job text, and Sidekick captures remain untrusted. Recognized instruction/role/secret-exfiltration patterns are rejected before sharing; instructions passed to the provider identify all source strings as data. The adapter offers no tools, code execution, link access, or mutation capability. Only a bounded, validated citation/classification structure reaches the UI, rendered as escaped React text. Pattern detection cannot comprehensively identify prompt injection; constrained capabilities and output validation limit its effects even when detection misses one. They do not guarantee correct classifications.

## Ownership, persistence, and deletion

Migration `0005_matching.sql` adds an application `description_revision` updated by a database trigger only when description text changes, `matching_previews`, `matching_reports`, and independent `matching_usage` counters. Existing migrations, resume bytes, document IDs, submitted links, and the JSON v1 contract remain unchanged. Every report records owner, application, exact resume-version ID, job revision and SHA-256, configuration identity, creation instant, source snapshot, and validated results or safe failure code. Failed attempts discard extracted sources.

The same-origin Node `/api/matching` boundary requires an uncached live verified session, verifies parent ownership, rejects cross-origin requests and stale-account headers, bounds requests to 4 KiB, and accepts IDs/actions rather than client-supplied sources or owners. Every SQL operation is owner-scoped. Composite foreign keys forbid cross-account resume/application references. A transaction locks the owner's workspace and uses a shared advisory lock for global usage reservations, so concurrent requests cannot exceed daily caps. Extraction admission also uses database locks across server processes.

Uploading version 2 never changes version 1 reports. A changed job description marks an earlier report **Previous job description**, even if the description is later reverted to its earlier wording. Status or unrelated edits do not make it stale. Description and configuration must still match the reviewed preview when the user confirms. Historical reports keep their sources and configuration; rerunning is explicit and never replaces older reports silently.

Reports restrict application/document deletion; archive remains safe. Delete derived reports explicitly before deleting a referenced document/application, subject also to existing interview/submitted-link rules. Running reports cannot be deleted. Previews cascade when their parents disappear. Existing JSON replacement is blocked while reports or submitted links exist, both at preview and confirmation. Derived reports can be deleted from application details without altering original applications, files, or usage counters.

Previews expire after 15 minutes. Running attempts older than five minutes become interrupted failures on later comparison access and are not retried automatically. Finished reports and reviewed text expire after 30 days and are removed on the owner's next comparison access. **Cleanup is opportunistic: inactive accounts can retain expired text longer. There is no scheduled purge or strict wall-clock deletion guarantee.** Usage counters remain for cost accounting and are not resume content. A future retention worker/account deletion design needs separate scope.

## Recovery and test isolation

JSON v1 exports do not contain comparison reports, reviewed text, description revision metadata, or document metadata/bytes/submitted links. They are application/interview exports, not complete account recovery. The operator database/manifest/file bundle includes reports, reviewed sources, usage, exact job revisions, and referenced files. The existing consistent PostgreSQL snapshot applies to matching tables; no external provider state is needed for report recovery. Restoring preserves completed reports/usage, discards previews, and marks in-flight attempts interrupted while clearing their sources. It revokes sessions and recovery tokens as before. Backup compatibility requires the exact new migration ledger. Older bundles require their matching code revision before a separately tested upgrade. See [recovery](DATABASE_RECOVERY.md).

Automated tests use deterministic injected providers and actual filesystem/DB operations. Browser fixtures are enabled only by `FATS_AI_PROVIDER=test-fixture`, `FATS_AI_TEST_MODE=1`, and an exact matching loopback `_test` database. The UI labels every fixture **Automated test fixture — no live AI**. Normal account tests explicitly disable AI configuration and keys. No automated suite falls back to a live provider. `pnpm test:e2e:matching` runs the focused desktop/mobile flow; `FATS_TEST_PRODUCTION=1` runs it against the optimized server after a production build. Live provider testing requires separate authorization, synthetic content, explicit budget, and consent; it was not performed for this phase.
