## Implemented behavior

Settings uses the existing `fats-backup` JSON format and `/api/workspace` export/preview/confirm flow. Accounts with offers export version 2; workspaces without offers continue to export version 1. Version 1 imports retain explicit replacement and existing preservation guards. Version 2 requires a verified account, adds missing applications/interviews/offers, skips identical records, and blocks the whole import on conflicts. No existing decision or revision is overwritten or merged. An identical reimport or repeated applied-token confirmation does not append history again.

Portable offer data includes full terms with exact decimal salary strings, checklist/questions, every review snapshot, dated negotiation notes, decisions, original request IDs, recording sequences, occurrence dates, and recorded timestamps. Validation rejects missing parents, duplicate offers/requests, missing/reordered sequences, unsupported/ownership fields, malformed metadata, live document links, and current state/review inconsistent with history. JSON is unsigned user-entered data; validation cannot establish the truth of its contents or who authored it.

PDF/DOCX bytes and complete document/version metadata remain excluded. Each historical letter UUID can survive as `documentReference`, but all new imported letter references remain unlinked. A matching destination UUID or filename does not create a download link. The preview names affected applications and history entries, and restored detail explains that the letter was not included in JSON. Reexport preserves that provenance. Existing live links on identical skipped offers remain intact.

Migration `0007_portable_offers.sql` adds only nullable `offer_events.source_version_id`, constrained to a terms entry without a live version link. It conveys no ownership, authorization, or file identity claim. Existing immutable-history protection covers it. No new dependency, table, endpoint, byte-storage adapter, or separate backup system was introduced. The intended local database must be migrated explicitly before running the updated account server.

## Remaining limits and excluded work

- Version 2 imports are additive whole records, not field-by-field merges or replacement. A conflicting record must be resolved deliberately; the importer does not discard or rewrite saved decisions/history.
- JSON cannot reconstruct a letter's file/version relationship. It preserves non-document history and unlinked provenance. Complete recovery of live links, file bytes, authentication, submitted resumes, and comparison records still requires the matching trusted operator archive/manifest/file bundle.
- JSON is private but unencrypted/unsigned, limited to 10 MiB, and requires a deliberate download and manual restore. A successful download request does not prove durable off-device storage.
- Guests retain version 1 local recovery and cannot import version 2 history. Browser transfer also remains version 1.
- Account deletion evidence covers the new restored history/provenance lifecycle; the existing document cleanup requirements still apply when that account owns real private bytes.
- NOT RUN: deployment, hosted/off-device recovery, real-employer actions, live AI/provider evaluation, or Career Vault. None is authorized. SKIPPED: unrelated matching/extension browser suites; their implementations/protocols were unchanged.
