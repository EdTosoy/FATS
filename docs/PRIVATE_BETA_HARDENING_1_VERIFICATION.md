## Data lifecycle audit and guarantees

| Store                                                                             | Ownership and erasure behavior                                                                                                                                                                                                                                  |
| --------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Applications, description revision, interviews and notes                          | Owner-scoped relational deletion, children before parents; the description revision is on the application row, not a separate archive.                                                                                                                          |
| Offers, immutable revisions, negotiations, decisions, checklists and questions    | Delete history, then offer headers before applications or document versions. Normal history restrictions remain intact; no trigger or foreign key is disabled.                                                                                                  |
| Documents, immutable version metadata, defaults/archive flags and submitted links | Delete links and historical dependents first, queue every tracked version/object, then delete metadata. Bytes and partials are removed through `DocumentStorage`.                                                                                               |
| Matching                                                                          | Delete historical previews/reports, reviewed sources, result/configuration/job metadata and owner-specific usage (`owner` and `extract:owner`) without enabling matching or calling a provider. Global aggregate counters have no owner identity and remain.    |
| Auth                                                                              | Revoke every session at the deletion checkpoint; delete password/account records and user in relational cleanup. Remove reset records by owner value and the hashed email-verification OTP identifier using the installed Better Auth 1.7.8 format.             |
| Backup/migration staging                                                          | Workspace restore previews (including embedded offers/notes), applied tokens, transfer fingerprints, workspace revision and upload budgets cascade with the user. No server copy of downloaded user JSON exists.                                                |
| Sidekick                                                                          | No server handoff/draft table. Pending capture is in extension `chrome.storage.session`; panel/web drafts are client state. A saved capture is an ordinary application and is erased. Closing/clearing those client contexts remains separate.                  |
| File intent / garbage / erasure job                                               | Durable ownership survives SQL rollback and user removal until acknowledged file cleanup. Completed jobs retain only a random receipt hash and request/completion times; owner UUID is cleared. This is minimal retry bookkeeping, not personal record history. |
| Other systems/copies                                                              | Mailpit messages, exported JSON/downloads, browser guest records, browser memory, operator archives/WAL/snapshots and any historical provider copies are outside live-account erasure. No automatic external purge is claimed.                                  |

Settings requires a checked consequences statement and exact `DELETE MY ACCOUNT` text. The server independently requires exact same origin, a live verified session and a matching current-account header, rejects caller-supplied ownership, and validates confirmation. The browser generates a 256-bit private receipt; only its SHA-256 hash is stored. A receipt can resume/check its own already-authorized job after session revocation; it grants no account read access and cannot start another account's deletion. Do not put receipts in URLs, logs or shared screenshots.

Deletion has separate durable steps:

1. Under the auth-operation lock and user row lock, commit an erasure marker, revoke sessions and remove recovery credentials. **This committed checkpoint is when deletion begins.** Requests authenticated before it must still pass the active-account check; mutations check again under a user row lock inside their transaction. Sign-in/recovery through the public allowlist cannot reactivate a pending account. A request whose storage transaction already holds the user lock finishes first, and its file key is included. Existing downloaded/client-memory bytes and responses already in flight cannot be recalled.
2. Recovery takes the same per-owner upload admission lock. A body/parser still running causes a truthful pending result; it cannot publish after the checkpoint. Relational cleanup queues all object keys and deletes children, user and auth records transactionally. SQL failure rolls this step back, preserving the earlier access block and cleanup request.
3. Unlink tracked `.blob` and deterministic `.partial` files and sync the directory. Retire each garbage/object record only after successful removal. Missing files permit idempotent retry. Storage errors, crash after unlink, ambiguous SQL result or failed final bookkeeping retain durable retry state. Complete means no owned intent remains. SQL and filesystem deletion **are not atomic**.

Migration `0008_data_lifecycle.sql` backfills ownership for existing referenced versions, adds file intents, erasure jobs and upload budgets. Every new file write has a committed intent before publication. Recovery locks the owner and waits for ambiguous SQL publication to settle before classifying intents without live versions as garbage. Ordinary file deletion uses the same durable cleanup implementation. No filename/age scan authorizes deletion.

**Important operational limits:** earlier untracked `.partial`/`.blob` files and pre-migration garbage without owner metadata cannot be attributed retroactively. Inventory and reconcile those privately with the application stopped; do not guess an owner or silently delete them. Cleanup assumes the configured private root is the original matching byte store. Do not switch to an empty root and claim old files were erased. Unlink is logical removal, not certified forensic erasure of SSD/journal/snapshot media. PostgreSQL logical deletion does not scrub old pages or WAL. Restoring an older archive can resurrect deleted accounts; an independently retained, access-controlled deletion register and a restore reconciliation/backup-expiry policy are still operational blockers.

## Recovery operation

After the server acknowledges deletion, the client unmounts its account workspace and uses a separate in-memory progress view. Owner-specific BroadcastChannel messages clear other active tabs for that account; no receipt or personal record is broadcast. The initiating progress view can retry with its receipt. Previously downloaded bytes, developer-tool copies or suspended clients cannot be remotely recalled. If the page/process closes, the local operator runs:

```sh
pnpm data:cleanup
pnpm documents:check
```

Use the intended database **and its matching original private directory**. `data:cleanup` resumes only durable deletion requests and reclaims tracked unpublished intents, excluding active uploads and referenced files. It prints aggregate pending counts only, returns unsuccessful while pending work remains, and can be rerun. It does not delete unknown inventory. It is not a scheduled service: operators must run it after interruption/restart and monitor failures. The read-only audit remains read-only. No normal development database was selected for tests.

After restoring an operator bundle, keep FATS stopped until cleanup and audit finish against the fresh restored directory. The archive retains pending erasure state/intent metadata, but the file bundle intentionally includes only live referenced versions. Missing non-live bytes are safe to acknowledge. Old backups require their original migration revision and a separate reconciliation policy; no historical archive was rewritten or destroyed here.

## Server upload and processing limits

| Boundary         | Enforced value / behavior                                                                                                                                                                                                                                                                       |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Raw upload       | Nonempty, at most **10 MiB**, counted from actual chunks regardless of Content-Length; one fixed-size buffer, no unbounded chunk array or multipart buffering. Invalid/excess Content-Length is rejected.                                                                                       |
| Body lifetime    | **30 seconds** total, including stalled chunk reads; cancellation on timeout/abort/error and release of admission. Parser work has its own bound below.                                                                                                                                         |
| Admission        | **1 upload per owner, 2 globally** across processes sharing PostgreSQL, acquired before reading/processing the body and held through publication. Excess attempts return 429; locks release on failure/connection loss.                                                                         |
| Attempt budget   | **20 admitted attempts per account per database-clock hour**, including invalid/interrupted bodies. This is an hourly bucket, not a rolling window or public-network abuse solution.                                                                                                            |
| Existing quotas  | **100 MiB** referenced bytes/account, **50** documents including archives, **20** immutable versions/document. Queued/unpublished bytes can exceed the live quota until recovery; there is no global disk-headroom guarantee.                                                                   |
| PDF              | Existing signature/end marker, pinned parser structure/encryption/active-action checks, **1–500 pages**, **100,000** inspected object visits, **5-second** worker deadline.                                                                                                                     |
| DOCX             | Classic stored/deflate ZIP only; **500 entries**, **20 MiB/entry**, **40 MiB total** declared and actual expansion, CRC/directory/path/required-parts checks; expansion cannot exceed **max(1 KiB, 200 × compressed bytes)** per entry. No recursive archive extraction.                        |
| XML              | Namespace-aware parsing, **100 nesting levels**, bounded node count (100,001 recorded nodes maximum), no DTD/entities. Macro declarations, ActiveX and embedded-object entries remain rejected.                                                                                                 |
| Worker           | PDF and DOCX validation run outside the main JS thread, **128 MiB old generation / 16 MiB young generation / 4 MiB stack**; completion/failure/timeout awaits termination. Parser stdout/stderr is drained without forwarding contents.                                                         |
| Local extraction | DOCX uses the same bounded worker/parser and existing 24,000-character/200-segment limits; PDF retains 30-page/10-second extraction bounds. No external analysis is requested.                                                                                                                  |
| Storage          | Opaque server UUID keys; no filename becomes a path. Private canonical directories, exclusive/no-follow publication, synced files/directory, immutable metadata, bounded reads and SHA-256 integrity checks remain. Durable intent covers failed publication, partial bytes and lost responses. |

The limits are server-side. File MIME/extension alone never determines acceptance; malformed PDFs, misleading extensions, malformed/deep/expanding DOCX and unsafe paths are rejected. Errors explain choosing a supported unencrypted/simpler file, retrying an interrupted upload or waiting for admission, without exposing parser/database/filesystem diagnostics. The existing mobile library and form draft behavior remain.

These worker limits do **not** bound all native allocations, ArrayBuffers, total process RSS, kernel I/O or a malicious parser exploit. Workers share the server process/security privileges. A process/container-level resource boundary and measured host capacity remain necessary before real/untrusted files.

## Malware boundary

No `clamscan` or `clamdscan` executable was available. **No malware scanner, quarantine, content disarm or clean-file certification is implemented.** A no-op scanner interface would not provide immediate protection, so none was added. Signature/structure/active-content checks are validation, not scanning.

A future bounded milestone can insert a fail-closed scanner/quarantine step **after bounded admission/intake and before parser invocation/publication**, with private bytes, scanner deadlines, explicit unavailable/infected states, scanner definition maintenance and synthetic scanner failure tests. Original downloads must remain inaccessible until the approved checks pass. Do not introduce a public scanning API or send resumes to a third party without separate authorization. Scanner closure alone would not remove the parser isolation blocker.

References: installed Next 16.4.0 route-handler guide and Better Auth 1.7.8 token/OTP source; [Node 24 worker resource limits](https://nodejs.org/docs/latest-v24.x/api/worker_threads.html#new-workerfilename-options) explicitly exclude external memory; [OWASP File Upload Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html) distinguishes validation, decompression limits, private storage and malware scanning. The new parser module is traced into the Next document/matching routes; no package dependency or lockfile changed.
