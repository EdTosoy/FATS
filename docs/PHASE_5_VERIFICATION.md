# Phase 5 — resume and document management verification

Implemented locally on 2026-10-15 with Node 24.21.0, pnpm 11.27.0, PostgreSQL 17, Next 16.4.0, and sandboxed system Chromium. No deployment, cloud storage, commit, push, or publication was performed. The pre-existing `apps/web/next-env.d.ts` change is preserved. No development/user database or browser workspace was used as a test target.

## Delivered behavior

Verified accounts have a private PDF/DOCX library with upload, categories, combined search/filter/archive controls, rename, immutable numbered versions, an explicit default resume, download, canvas PDF preview, and confirmed unlinked deletion. Application details explicitly record an exact submitted resume version. New uploads, renaming, default changes, and archiving leave that association unchanged. Linked documents retain downloadable history and cannot be deleted. Guests keep the existing tracker/interview/Sidekick workflows and see a sign-in explanation for documents. The dashboard adds one small contextual document step.

Migration `0004_documents.sql` adds owner-scoped documents, immutable versions, application/version associations, and a durable deletion queue. Existing SQL migrations and all four moodboard files are unchanged. Composite foreign keys enforce account ownership and restrict references; a partial unique index permits one active default resume. Every API operation derives ownership from a live verified session. Private UUID storage keys and raw filesystem paths never appear in document API metadata.

`DocumentStorage` separates metadata from bytes. The local adapter uses an absolute canonical persistent directory (0700), exclusive/synced file publication (0600), no-follow bounded reads, and SHA-256 checks. Metadata is committed only after complete durable bytes exist. Upload request IDs permit safe retries. Partial/unreferenced files never appear as complete documents. Deletion queues physical cleanup only after metadata deletion commits; storage failures retain retry entries. The read-only operator audit reports aggregate integrity/orphan/partial/pending-deletion counts without exposing private metadata.

Limits: 10 MiB/file, 100 MiB/account including history/archives, 50 documents/account, 20 versions/document. PDF structure/encryption/active-content checks run in a bounded native worker. DOCX validation checks classic ZIP structure, CRC, bounded decompression, required Open XML parts/types/relationships, XML namespaces, and forbidden DTD/macros/embedded objects. Browser MIME labels have no authority. PDF.js 6.4.299 paints canvas pixels without HTML/annotation/scripting/XFA layers; the renderer is bundled locally and tested for actual painted content. Original downloads remain private, authenticated, uncached, and served with attachment/MIME/nosniff/sandbox headers.

Pinned additions are pdf-lib 1.17.1 for server structure/action inspection, saxes 6.0.0 for namespace-aware XML validation, PDF.js 6.4.299 for safe canvas rendering, and development-only fflate 0.8.2 for DOCX fixtures. The lockfile was reviewed, including PDF.js optional native canvas packages; no build-script approval or cloud SDK was added.

## Recovery boundary

Settings version 1 JSON exports contain applications/interviews only. They exclude document metadata, bytes, and submitted links. JSON replacement is blocked while links exist, including changes after preview, so it cannot silently discard submitted history. Additive browser transfer is unchanged.

Complete local operator recovery requires a PostgreSQL dump, version 2 manifest, and matching `.dump.documents/` file directory. A global advisory lock excludes document mutations while one database snapshot and verified immutable files are copied. Missing/corrupt/unavailable source bytes prevent a complete backup. Restore requires a separately selected database, a fresh independently selected private file directory, compatibility preview, stopped application, and the exact existing destructive confirmation. It verifies/copies bytes before transactional schema/data/inventory checks and token/session revocation. Files remain private after an attempted SQL restore fails or has an uncertain result, protecting against a lost commit response. Keep the app stopped and inspect before selecting a fresh target for retry.

See [storage/ownership/version design](DOCUMENTS.md), [database and file recovery runbook](DATABASE_RECOVERY.md), [JSON limits](BACKUPS.md), and [local configuration](LOCAL_CONFIGURATION.md).

## Findings corrected during verification

- Native Node operator imports require erasable TypeScript and explicit file extensions; the storage error class and shared no-emit TypeScript configuration now support those imports.
- Next/Turbopack rewrites static module resolution to virtual IDs. PDF validation now resolves its installed parser inside the native worker; real browser uploads verify that path.
- A native PDF frame is blocked by Chromium under a strict sandbox. It was replaced by local canvas rendering; tests verify nonblank pixels and screenshots were inspected.
- Controlled dialogs without a Radix trigger needed explicit opener focus restoration. Native select accessible names and filter-reset focus were corrected.
- The old account browser assertion assumed a single status region; it now targets the existing progress card, retaining its exact behavior assertion.
- Failed SQL restore retains copied private files after a restore attempt rather than risking deletion after an uncertain commit response.

## Known limitations and next step

This is a verified local Linux/Node/filesystem implementation, not hosted readiness. The local Next server uses the installed parser package from its workspace; a future standalone/container artifact must separately verify dependency tracing and packaging. Files/archives are private by filesystem permissions and application authorization but are not encrypted at rest by FATS. A volume/local copy alone is not an off-device backup. No S3 adapter, deployment, automatic backup schedule, durable upload queue, malware scanner, content-disarm service, or background orphan collector is implemented. Heap/time limits and format parsing are not malware certification or a complete native-memory isolation boundary.

PDF 1.0–1.7 and classic ZIP/UTF-8 transitional DOCX are supported; encrypted files, PDF 2.0, ZIP64, strict OOXML namespaces, macros/embedded objects, and unsupported encodings are rejected. Preview paints one page at a time and omits interactive layers; some fonts/image encodings need the original download. DOCX has no browser preview. Individual versions cannot be deleted; deletion applies to an entire unlinked document. Quotas count referenced bytes; retained partial/orphan/deletion-queue files can occupy additional disk space. Operators must monitor storage and inspect a stopped database before any separately authorized manual orphan cleanup.

Firefox/WebKit, native mobile browsers, full assistive-technology/accessibility conformance, manual Chrome native side-panel docking, Windows/macOS filesystem behavior, hosted storage, and off-device disaster recovery were not tested. Extension automation retains the existing packaged-panel/native-dock limitations.

Recommended next implementation step: separately scope managed orphan cleanup, deployment-specific storage isolation/malware scanning, encrypted off-device archives, hosted account delivery/abuse controls, and a hosted recovery rehearsal before inviting external users. Stop after Phase 5.
