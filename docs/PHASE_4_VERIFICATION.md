Historical Phase 4 baseline. Required email verification, password recovery, and operational database archives are now covered in [Phase 4.1 verification](PHASE_4_1_VERIFICATION.md).

Implemented and verified locally on 2026-10-15 with Node 24.21.0, pnpm 11.27.0, PostgreSQL 17, and system Chromium. This continuation started with substantial uncommitted Phase 3/4 work. Existing work and all four moodboards were preserved. No commits, pushes, cloud resources, external publishing, deployment, or later-phase features were authorized or performed.

## Architecture and schema

[ADR 0001](decisions/0001-authentication-and-persistence.md) chooses Node Route Handlers in the existing Next.js 16.4 application over NestJS. One web runtime avoids a second service, API configuration, and cross-origin cookies. Better Auth 1.7.8 owns authentication; `pg` handles parameterized application queries. Kysely supplies Better Auth's supported PostgreSQL dialect. No application ORM, microservices, or cloud infrastructure were introduced.

The UI's existing repository boundary is retained. `WorkspaceRoot` injects `HttpWorkspaceRepository` for an account and the existing local adapter for guests. Account data is held in memory, never written as a browser-local cache. The domain remains independent of React, Next, and SQL. All server writes validate domain rules again.

Migrations in `apps/web/migrations`:

| Migration              | Purpose                                                                                                                                               |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `0001_auth.sql`        | Library-generated user, account/password, session, verification, and database rate-limit tables/indexes.                                              |
| `0002_workspace.sql`   | Applications, interviews, workspace revision/locking, owner-bound preview stages, and completed local-transfer fingerprints.                          |
| `0003_legacy_text.sql` | Preserve valid version 1 backup whitespace without redundant raw SQL length checks rejecting it; shared server validation still enforces field rules. |

The runner takes a transaction-scoped advisory lock, checks immutable SHA-256 migration checksums, and applies pending SQL and ledger entries in one transaction. Tests cover reruns, changed checksums, failed DDL rollback, and a genuinely empty database. Apply migrations **before** starting Better Auth, which starts schema validation during initialization. Restart the web process after schema changes. The schema generator refuses to overwrite an existing initial migration.

Application/interview primary keys are `(user_id, id)`; a composite parent foreign key prevents cross-account links and restricts application deletion while any interview exists. Legacy string IDs up to 256 characters are preserved independently per account. Status constraints retain every existing status. `timestamptz` stores UTC instants alongside the explicit interview IANA timezone. New writes use server timestamps; imports preserve original timestamps and text. Scheduling never updates recruitment status.

Workspace row locks serialize related writes and Sidekick duplicate checks. Reads use a consistent repeatable-read snapshot. Ordinary edits retain the existing last-successful-write behavior; previewed replacements and migrations additionally reject a changed workspace revision. Failed inserts and replacements roll back completely.

## Authentication and security boundaries

- Email/password registration, login, and logout use Better Auth. Password policy is 12–128 characters; the installed library supplies salted scrypt hashing. No application cryptography is implemented.
- Database-backed sessions expire after seven days and renew after one day of activity. Cookie caching is disabled; the server checks live sessions and immediately rejects logout-revoked/expired sessions. Logout revokes the current session, not every device.
- Cookies are HTTP-only, SameSite=Lax, path `/`, and Secure for HTTPS. Non-loopback HTTP auth origins are rejected. Local HTTP cookies intentionally lack Secure. Exact configured Host/Origin checks, Fetch Metadata checks, same-origin JSON writes, bounded request bodies, and the library's auth defenses restrict requests.
- Database-backed auth rate limits are enabled. This local server trusts no forwarded client-IP headers, so limits use a shared per-path bucket (20 sign-ins/minute, 30 registrations/minute). Hosted proxy/abuse policy needs separate deployment work.
- Every record query includes the owner derived from a validated server session. Client ownership fields cannot select an owner. A client account header detects a stale tab and blocks saving into a changed account; it grants no access.
- Auth routes expose only registration/login/logout/session checking. Responses project name/email/ID and strip auth/session tokens from JSON. Errors use safe messages; private responses are not cached. SQL values are parameterized; captured descriptions remain escaped text.
- Secrets are generated into ignored, private environment files. Example values are placeholders. PostgreSQL ports bind only to loopback. No credentials are sent to the extension or captured pages.

The installed library's session, password, cookie, rate-limit, and schema-check source/types were inspected. Official references: [session management](https://better-auth.com/docs/concepts/session-management), [email/password](https://better-auth.com/docs/authentication/email-password), [cookies](https://better-auth.com/docs/concepts/cookies), [rate limiting](https://better-auth.com/docs/concepts/rate-limit), and [security](https://better-auth.com/docs/reference/security). Next Route Handler behavior was checked in the installed Next 16.4 documentation.

## Local migration, recovery, and compatibility

The existing `fats.applications.v1` envelope and `fats-backup` version 1 stay compatible. Phase 1 envelopes without interviews still load as an empty interview collection. Registration/login never upload local records.

Settings detects local records and explains the separate workspaces. Preview shows incoming/new/identical counts, followed by an explicit confirmation checkbox. The client detects local changes since preview. The server validates every record, parent, status, timestamp, timezone, and URL, stages an owner-bound snapshot for 15 minutes, then rechecks the account revision before an additive transaction. Identical records are skipped; matching IDs with different contents stop the entire transfer without overwriting either workspace. Keep both exports before resolving conflicts.

An owner/snapshot fingerprint persists completion. Repeated or concurrently confirmed imports do not duplicate records; retrying a committed stage after a lost HTTP response returns the current workspace. A failed PostgreSQL write leaves no partial records or completion ledger. Original local data is never erased or rewritten. Already transferred snapshots are not reapplied after subsequent account changes; recovery uses the separate, deliberate backup restore flow. Expired stages are cleaned opportunistically on future previews.

Phase 2.1 export/preview/confirmed full replacement remains available for both active account and guest workspaces. Account restore uses a database transaction and owner/revision-bound stage. Export excludes credentials, sessions, unrelated storage, and unsaved drafts. Sign out to access local recovery. Backups remain private and unencrypted. A database volume is not an independent backup.

Session expiration keeps mounted form inputs, blocks account writes, and offers sign-in in a new tab. It never silently falls back to a browser write. Reloading an expired account shows a reconnect gate. Logout/account changes remount and clear the account view.

Sidekick retains Capture → Review → Open FATS → Confirm → Save. Guests can sign in and return to the opaque handoff fragment. Return to `/sidekick` uses a full document navigation so Chrome reinjects its narrowly matched bridge; SPA navigation alone did not. The extension's original permission, origin/path/sender, expiry, and plain-text boundaries remain. Account duplicate checks run under the workspace write lock.

## Known limitations and next slice

This is a local foundation, not a deployed hosted service. Email ownership verification, password recovery, production proxy/rate-limit policy, operational backup/restore, and public registration abuse controls remain separately scoped prerequisites. There is no account deletion UI, global session-management UI, per-record conflict UI, offline account cache, or deletion UI for tracked records (delete APIs enforce ownership and parent restrictions). Browser profiles sharing an account cookie share that account access. Guest storage retains its original simultaneous-writer limitation.

The test container is disposable; the development Compose volume is persistent. Neither is a disaster-recovery strategy. Unsaved forms/pending Sidekick drafts are not backed up. Sidekick still supports only the two documented loopback origins and its 15-minute handoff validity. Native Chrome dock usability, Firefox/WebKit, native Safari, assistive technologies, a full accessibility audit, and hosted operation were not tested.

Recommended next slice: separately scope hosted-account readiness and recovery before resume document storage. No resume uploads, AI, payments, email automation, crawling, or deployment work is started. Stop after Phase 4.
