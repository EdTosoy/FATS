## Acceptance and security evidence

The real account journey starts empty, creates a first Current employment, survives a synthetic HTTP save failure with form inputs intact, then saves through UI → same-origin API → PostgreSQL → reload. It creates a requested COE metadata entry, records request/follow-up dates and notes, changes it to Received with an issue date, and displays both prior and current snapshots. It changes employment to Previous with an end date, archives it and retrieves it after reload. The browser confirms no upload PUT, no account employment/notes in localStorage, no horizontal page overflow and no unhandled page errors.

A separate journey imports an existing accepted offer through the established JSON flow, explicitly prefills a new employment, verifies it remains Not started and creates no automatic document entries. It records a BIR entry as Not applicable, exports version 3, previews/confirms import into another verified synthetic account, and verifies identical employment/register history and the application connection. Repeated import skips the record without duplicating events. Another journey restores unlinked file provenance, shows no download link and blocks conflicting later history without changing saved records.

PostgreSQL tests verify planned/current/previous transitions, original timestamps/history, immutable event triggers, idempotent request fingerprints, stale-version rejection, duplicate job/application checks, all document tracking states, optional dates/tax year/notes, owned accepted-offer associations and historical parent protection. Real authenticated handler tests cover missing/unverified sessions, exact origin, stale account headers, ownership injection, private responses and live account availability.

Accepted-file relationship tests use the existing internal **synthetic scanner fixture**, never a production configuration or antivirus claim. They verify exact private version linking, fresh hash/byte checks, cross-user denial, corrupt-byte failure, legacy/quarantine rejection, blocked downloads, protected historical files and metadata updates without a file. Identical self-import keeps the existing authorized relationship. A new import keeps every file reference unlinked even when the destination owns an accepted version with that exact UUID. No bytes are copied. Erasure blocks further career access/writes, removes career history before protected parents, deletes linked private versions and completes durable file cleanup.

Version 3 validation rejects forged live file links, owner/storage fields, missing application/accepted-offer history, duplicate IDs/requests/jobs, mismatched current/history snapshots, invalid dates and unsupported counts. Existing version 1/2 unit/browser regressions pass. Version 1 replacement protects vault history; version 2 additive import preserves it. Revision changes from Career Vault invalidate staged restores, conflicts block all additions, repeated confirmation is idempotent, and failed/stale imports leave saved data intact. Full operator recovery was executed only against independently selected disposable databases with exact confirmation, not a user restore target.

PDF Tools source and byte-processing behavior remain unchanged. Its representative local employment-form journey is included in the guest regression pass: original-byte hashes, actual exported-PDF reopening/rendering at four page rotations and a nonzero crop origin, typed/drawn signatures, resource/error cases, zero write requests and no external request origins. ## Browser evidence and limitations

Final screenshots are retained separately under `test-results/career-account/` and guest evidence under the guest test output. Employment/register history at desktop/mobile, the import preview/conflict dialog and the guest empty explanation were visually inspected. The import preview's Offer history heading was moved beside its offer details after screenshot review. Native labels, dialog focus/cancellation, narrow layout, truthful file messages and ordinary keyboard interactions were checked. Long import dialogs scroll within the viewport. This is representative Chromium emulation, not WCAG certification, real-device or screen-reader testing.

The JSON backup is private and unencrypted and excludes actual files/live links. Limits remain 50 employments/account, 100 snapshots/employment, 30 register entries/employment and 10 MiB combined JSON. Drafts have no durable autosave or cross-device recovery; archive preserves rather than deletes history. Parent/file references can deliberately restrict ordinary deletion. A large or saturated history requires export/operator assistance rather than silent pruning.

Live ClamAV configuration/verification remains paused and Hardening 2 partial. New-file saving is unavailable; Received metadata is not storage proof. Real-data beta still needs intended-runtime containment/headroom and operational supervision, retention/deletion/backup-WAL policy, protected off-device recovery, hosted account email/HTTPS/restricted access, monitoring/privacy/support ownership and broader accessibility evidence. No real personal files, production deployment, live employer/government integration or notification service was tested or authorized.

Recommended next milestone: a synthetic graduate walkthrough plus retention/recovery rehearsal, refining observed friction while keeping scanning and AI paused. Live intake or accepted-file handoff to PDF Tools needs separate authorization and actual scanner verification.
